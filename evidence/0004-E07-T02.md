## Implemented

- The app publisher rebuilds every packet projection from the durable event log before
  publication. It reconciles, in order, the last verified public union, the independently
  published repository migration export, and the durable app records. A later source wins
  the entire record by packet id, so the current repository replaces an older repository
  projection, the app wins a migrated duplicate, and no id appears twice.
- Publication runs synchronously after issue, including issue of a supersession. Draft
  creation and editing, comments, takes, and status transitions do not publish. This
  issue-only trigger avoids a new Hosting release for every write.
- The publisher clones the current live Hosting version, replaces only `/packets.json`,
  uploads by content hash, finalizes, and creates a live-channel release. No failed step
  changes the live release. It uses Application Default Credentials from the attached
  runtime service account and the `firebase.hosting` OAuth scope; no key or long-lived
  credential is configured.
- Git publication remains during migration. Deployment writes the repository-only source
  to `/repository-packets.json` and renews the verified public union without changing its
  payload digest, so a code deploy does not intentionally rebuild `/packets.json` from git.
- An unreachable Firestore store or unverifiable publication source starts the service in
  explicit read-only mode from the last verified export. Authoring then returns HTTP 503
  `store_unavailable`; it never falls back to an empty or in-memory store.
- App provenance is `tracker.martcoca.com/app` at the deployed `SOURCE_COMMIT`; git
  provenance remains `martcoca/work-tracker` at the publishing merge commit. Both use the
  existing six-field envelope, packet schema, digest, and `contract.FreshnessBound`.
