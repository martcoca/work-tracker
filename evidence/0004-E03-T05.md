# Evidence: 0004-E03-T05

## Result

Every newly issued agent credential now carries two separate records:

- a tenant-scoped workload principal: `kind`, `issuer`, and `subject`; and
- a product-local binding: packet, attempt, issue time, and expiry.

The human creation request names the workload tenant, issuer, and subject. The service sets
`kind: workload`; it does not accept a caller-selected kind. The named workload tenant must
equal the tenant in the verified human identity. A mismatch returns HTTP 403
`workload_tenant_mismatch`; an absent or malformed issuer or subject returns HTTP 422
`invalid_workload`.

The explicit workload tenant is checked and discarded at creation. Stored metadata and the
authenticated identity carry one enclosing `tenant_id` beside the exact grant principal
shape. This avoids two stored tenant values that could diverge while still making a
cross-tenant request distinguishable.

The authenticated identity serialized with exactly these top-level fields:

```json
{
  "tenant_id": "tenant-a",
  "workload": {
    "kind": "workload",
    "issuer": "https://identity.invalid",
    "subject": "workload-a"
  },
  "binding": {
    "packet_id": "0004-E03-T05",
    "attempt_id": "attempt-a",
    "issued_at": "2026-09-07T12:00:00Z",
    "expires_at": "2026-09-07T13:00:00Z"
  }
}
```

The identity test rejects any credential value, `credential` field, or scope field in that
serialization. Grant lookup can consume tenant plus `workload`; packet and attempt remain in
the separate binding and are never part of the grant principal.

## Demonstrations

The focused suites demonstrated:

```text
valid credential resolved to workload=https://identity.invalid/workload-a
packet=0004-E03-T05 attempt=attempt-a
detail and list contain workload metadata only; machine bootstrap refused
authenticated workload=https://identity.invalid/workload-a beside
packet=0004-E02-T01 attempt=attempt-e03-t05
verified empty agent-grants export refused with HTTP 403; last use recorded
unknown, malformed, revoked, and expired credentials returned distinct codes;
revocation affected the next request
```

The empty export is a verified, fresh `martcoca.identity.agent-grants/1` fixture. The
credential authenticates first, advances `last_used_at`, and then receives HTTP 403
`grant_required`. That is distinguishable from every HTTP 401 authentication refusal and
proves the workload contributes no authority by itself.

The existing machine refusals remain:

- `malformed_authorization` for an invalid bearer header;
- `unknown_credential` for an unknown identifier or wrong bearer value;
- `revoked_credential` immediately after revocation; and
- `expired_credential` at or after the binding expiry.

The Firestore document stores workload issuer and subject beside the existing digest and
binding metadata. Its schema is version 2 and its default namespace is
`agent-credentials-v2`. Pre-workload documents therefore cannot authenticate and cannot
break list decoding. No bearer field was added; only the SHA-256 digest remains durable.

## Mutation checks

Each production rule was disabled separately, its focused test was run, and the production
code was restored before the final suite:

- Removing issuer/subject request validation changed the malformed-issuer result from
  `ErrInvalidWorkload` to a stored-metadata validation error; the error-distinction test
  failed.
- Removing the HTTP `invalid_workload` mapping returned HTTP 500 instead of 422.
- Removing the workload-tenant comparison issued a credential and returned HTTP 201 instead
  of 403 `workload_tenant_mismatch`; the failure output withheld the response body.
- Removing workload from `List` returned empty workload metadata; the list test failed.
- Removing workload from the authenticated identity produced an empty workload; the exact
  identity test failed.
- Removing binding from the authenticated identity produced empty packet and attempt
  fields; the same identity test failed.
- Omitting workload subject from Firestore encoding made the round-trip fail with
  `stored credential is incomplete`.
- Accepting a header without `Bearer` changed the malformed-header error to nil.
- Disabling constant-time digest comparison changed the wrong-value error to nil.
- Disabling the revoked check made the first post-revocation authentication succeed.
- Disabling the expiry check made authentication at expiry succeed.
- Removing the `grant_required` mapping returned HTTP 500 `operation_failed` instead of the
  authenticated HTTP 403 refusal.

The tenant mutation initially exposed that the negative assertion included a creation
response body. Both creation assertions now withhold response bodies, so a deliberately
broken guard cannot place a one-time bearer in test output. No credential value is included
here.
