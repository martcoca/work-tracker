# Evidence: 0004-E05-T04

## Result

A rollback reaches a previous version, and a roll-forward brings production back. Both
were run against the live product on 2026-09-07. Two defects had to be fixed to get there:
the apply was erasing the pins a rollback reaches through, and the policy could not resolve
the one pin shape a roll-forward always presents.

## Why the rollback could not reach anything

Firebase Hosting's `pinTag` rewrite records a zero-percent `fh-` traffic tag against the
revision a Hosting version serves, and a released version routes `/api/**` through that
recorded tag. The tag *is* the rollback mechanism.

`traffic` was declared in `infra/deploy/main.tf` and not ignored, so the provider sent the
declared allocation on every update and dropped the tag Firebase had added. This is not
inference; it is the Cloud Run audit log for the deploy immediately before this work:

```
ts=2026-09-08T01:23:23Z
ua=Terraform/1.13.0 ... terraform-provider-google/dev7
traffic=[{"percent":100,"type":"TRAFFIC_TARGET_ALLOCATION_TYPE_LATEST"}]
```

Twenty-five retained revisions therefore carried exactly one tag, on the revision already
serving:

```
{"revisionName":"tracker-reader-00025-df5","tag":"fh-5e3048522f3d5e32","percent":100}
```

Every older Hosting version pinned a tag that no longer resolved, and the policy refused —
correctly. The only rollback the design permitted was a no-op.

## The retention choice and what it costs

**The apply ignores `traffic`.** Routing is `TRAFFIC_TARGET_ALLOCATION_TYPE_LATEST`, so it
follows the newest ready revision without being re-asserted; the pins are the one thing an
apply must not erase. The two things the apply was doing implicitly are now explicit and
failable in `scripts/deploy/prune-run-tags.mjs`, which runs after the Hosting refresh:

- it refuses any allocation other than one latest-revision target at 100% with zero-percent
  named pins — the drift the apply used to correct; and
- it keeps the newest `RETAINED_PIN_TAGS = 10` pins and reclaims the rest.

**Ten pins is ten deploys of rollback reach.** `firebase-tools`' `ensureLatestRevisionTagged`
reuses the pin already on the latest ready revision rather than adding a second, so a deploy
adds exactly one; the preflight release reuses the previous deploy's pin and adds nothing.
Its own tag garbage collector has a threshold of 500 and never fires at this size.

**Cost.** A pin is a zero-percent traffic target on a revision that already exists and
scales to zero: no compute, no storage, no request path. The bound is there because
unbounded growth is a leak, not because the eleventh pin is expensive. What it costs is
reach: a version older than ten deploys is not rollback-reachable, and asking for one is
refused rather than approximated.

**Coupling.** `scripts/deploy/check-workflow.sh` requires `ignore_changes = [traffic]` and
the retention step *together*, and requires the step to run after the Hosting refresh. An
apply that ignores traffic without the step would leave nothing checking the allocation.
Each of the three refusals was exercised by breaking it:

```
error: infra/deploy/main.tf is missing required delivery policy: ignore_changes = [traffic]
error: .github/workflows/deploy.yml is missing required delivery policy: node scripts/deploy/prune-run-tags.mjs
error: delivery must build, scan, push, build the export, publish it, verify, guard, apply, refresh Hosting, then bound its pins
```

## The pin a roll-forward always presents

With retention landed, the first live rollback succeeded and the roll-forward refused:

```
rollback refused: pinned Cloud Run revision is absent or malformed
```

Cloud Run keeps a pin on the latest ready revision as a named revision target in the service
spec, but merges it into the latest-revision entry of `trafficStatuses`, which reports
percent, tag and uri and no `revision` at all:

```
spec:   {"type":"TRAFFIC_TARGET_ALLOCATION_TYPE_REVISION","revision":"tracker-reader-00026-26c","tag":"fh-e6c8f51b73b38b11"}
status: {"type":"TRAFFIC_TARGET_ALLOCATION_TYPE_LATEST","percent":100,"tag":"fh-e6c8f51b73b38b11"}
```

Rolling *forward* to the commit currently deployed is exactly that shape, so the one
rollback that returns production to where it started was the one the policy could not
resolve. Rolling back never hit it, because an older pin is a plain revision target.

`selectPinnedRevision` now resolves a folded pin through the service's own
`latestReadyRevision`. Nothing is relaxed: `verifyRevisionProvenance` still requires the
resolved revision's `source-commit` annotation to equal the requested commit, and a folded
pin on a service naming no latest ready revision still refuses. Removing the resolution
fails its test.

## What this cost, and what is still true

The rollback in `0004-E05-T02` was never exercised against the live product, and both
defects found here were invisible to every test that existed. The packet's own clause said
it: *"A documented rollback that has never been run is not a rollback — it is a paragraph."*
Two of them, in this case — one in the infrastructure that fed it and one in the policy
itself.

Retention is bounded at ten deploys. That is a real limit, not a formality: a version older
than that is unreachable by design and refuses rather than guessing.
