## One-action rollback

The `Rollback` workflow is manually dispatched on `main` with one input, the full commit of
a version previously shipped by `Deploy`:

```sh
gh workflow run rollback.yml --ref main -f target_commit="$TARGET_COMMIT"
```

Roll-forward is the same one action with the commit that was live before rollback. The
workflow exchanges the existing exact-main workload identity for the deploy-only account;
it stores no credential and grants itself no new authority.

Before its single state-changing request, it requires all of the following:

- the commit is a full hash in the checked-out `main` ancestry;
- a retained live-channel Hosting release has a message exactly equal to that commit;
- the selected Hosting version is finalized and has exactly one pinned `/api/**` rewrite
  to `tracker-reader` in the configured region;
- the pin resolves to exactly one retained Cloud Run revision while the service is not
  reconciling; and
- that revision's `source-commit` annotation equals the target commit.

Only then does it create one live Hosting release for the already-finalized version.
Firebase Hosting stores the Cloud Run tag in that version, so the frontend and API route
move together. There is no independent Cloud Run traffic update that could silently pair
an old frontend with a newer API. The workflow finally reads the selected static commit
marker back through `https://tracker.martcoca.com` over TLS.

## Live evidence

Both runs are recorded, and neither worked on the mechanism as this packet left it. Running
`Rollback` against the live product found two defects, and the second was only visible after
the first was fixed:

1. **Nothing was reachable.** The deploy's apply declared `traffic` and therefore erased the
   Firebase Hosting pin on every update, so every retained revision but the one already
   serving lost its tag. The only rollback this mechanism permitted was a no-op, and it
   refused correctly: `Hosting pin does not resolve to exactly one retained Cloud Run
   revision`.
2. **The roll-forward could not resolve its own pin.** Cloud Run merges a pin on the latest
   ready revision into the latest-revision entry of `trafficStatuses`, which reports no
   `revision`. Rolling forward to the commit currently deployed is exactly that shape, so the
   one rollback that returns production to where it started was the one the policy refused:
   `pinned Cloud Run revision is absent or malformed`.

`0004-E05-T04` fixed both and ran the live rollback
([34178365374](https://github.com/martcoca/work-tracker/actions/runs/34178365374)) and
roll-forward ([34178548350](https://github.com/martcoca/work-tracker/actions/runs/34178548350)),
with independent readbacks of the frontend marker and of the Cloud Run revision that served
`/api/**`, plus live refusals for an unreachable version and for malformed input. The full
record, including the retention bound and its cost, is in
[`0004-E05-T04.md`](0004-E05-T04.md).

**What this packet got right and what it missed.** The policy it wrote is sound — every
refusal it built still stands, none was relaxed to make a rollback pass, and one of them
caught defect 1 rather than papering over it. What it missed is stated in its own clause:
*"A documented rollback that has never been run is not a rollback — it is a paragraph."* It
was never run. Both defects were invisible to every test that existed, because both live in
the gap between the policy and the platform it talks to.
