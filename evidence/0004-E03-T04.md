# Evidence: 0004-E03-T04

## Result

The tracker now issues product-owned agent credentials. A signed-in human can create one
for a packet in their tenant, list it, fetch its metadata, and revoke it. Creation returns
the bearer value once under `credential`; every later representation contains metadata
only.

The credential is `wta_<random-id>.<random-value>`, with 128 random identifier bits and 256
random bearer bits. The durable record contains only SHA-256 of the complete value. SHA-256
is appropriate here because the input is a generated 256-bit value rather than a human
password. The digest is explicitly excluded from JSON serialization.

Credentials reproduce 0000's session principal: packet id, attempt id, issued-at, and
expiry. Tenant is stored beside the principal for exact grant matching. Lifetime is limited
to one hour. The authenticated identity contains those fields and no scope or permission.

Production opens a separate credential collection in the already-applied Firestore
database. Authentication reads, checks, and writes `last_used_at` in one transaction.
Revocation updates the same document in a transaction, so a concurrent authentication
conflicts, retries, and observes the revocation rather than succeeding from an earlier
read. No infrastructure, IAM, identity configuration, or cloud resource changed.

## Demonstrations

The focused verbose suite reported:

```text
created credential 0102030405060708090a0b0c0d0e0f10;
retrieval exposes metadata only; stored digest was refused
valid credential resolved to kind=session packet=0004-E03-T04
last_used_at=2026-09-07T12:10:00Z
valid before revocation; the immediately following request was refused as revoked
```

The HTTP demonstrations reported:

```text
detail and list contain metadata only; machine bootstrap refused
authenticated as packet=0004-E02-T01 attempt=attempt-e03-t04
verified empty agent-grants export refused with HTTP 403; last use recorded
unknown, malformed, revoked, and expired credentials returned distinct codes;
revocation affected the next request
```

The machine-authentication seam placed `tenant_id` and the session principal on the
request. A downstream operation using a verified, fresh `martcoca.identity.agent-grants/1`
fixture with an empty payload returned HTTP 403 `grant_required` after authentication.
Authentication still recorded the use. This proves a valid credential contributes no
authority by itself without implementing E03-T01's comment or transition operations.

The refusal codes are distinct:

- missing or malformed bearer header: `malformed_authorization`;
- unknown id or wrong bearer value: `unknown_credential`;
- revoked: `revoked_credential`;
- expired: `expired_credential`.

A machine bearer presented to `POST /api/agent-credentials` was rejected by the human
Identity Platform verifier as `invalid_identity`; there is no agent bootstrap route. A
tenant could not create or retrieve a credential for another tenant's packet. Reading the
packet after credential creation contained neither the one-time value nor credential id,
and `packetexport` has no dependency on the credential packages.

## Mutation checks

Each production refusal was temporarily disabled, its focused test was run, and the rule
was restored:

- Accepting a header without `Bearer` changed the malformed-header request to HTTP 200.
- Disabling the shared constant-time digest comparison made the stored digest authenticate;
  `TestCredentialIsReturnedOnceAndOnlyItsHashIsStored` failed with `error = <nil>, want
  ErrUnknownCredential`.
- Disabling the shared revoked check changed the next post-revocation request to HTTP 200;
  its test wanted HTTP 401 `revoked_credential`.
- Disabling the shared strict expiry check changed the at-expiry request to HTTP 200; its
  test wanted HTTP 401 `expired_credential`.

Both the memory implementation used by tests and the production Firestore transaction call
the same digest/revocation/expiry function. The final focused suite passed after restoration.
