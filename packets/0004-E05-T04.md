## Context

`0004-E05-T02` built `rollback.yml` with sound policy checks, and it cannot roll anything
back. Running it twice against the live product found two defects; the first is fixed and
the second is this packet.

Firebase Hosting pins `/api/**` to a **tagged** Cloud Run revision. Each deploy tags the
new revision, and the previous tag is reclaimed. Live state on 2026-09-03:

```
17 revisions retained · 1 traffic tag

00017  8bf68db  tag fh-b448c0239cf415e2, 100%   ← the only reachable one
00016  61ab6ba  no tag
00015  36aba70  no tag
```

So a Hosting version from a previous deploy pins a tag that no longer resolves, and the
policy refuses — correctly:

```
rollback refused: Hosting pin does not resolve to exactly one retained Cloud Run revision
```

**The refusal is right and the mechanism is wrong.** Exactly one revision is ever reachable
by tag, and it is the one already serving, so the only rollback the design permits is a
no-op. The packet's own clause caught this: *"A documented rollback that has never been run
is not a rollback — it is a paragraph."*

## Goal

A rollback reaches a version that was previously live, and both surfaces move together.

## Boundary

**Do not weaken the policy to make a rollback pass.** Every refusal in
`scripts/deploy/rollback-policy.mjs` exists because a rollback that guesses is worse than
one that stops. If a check must change, say which and why it is still fail-closed.

**Do not pin Hosting to a revision the deploy has not verified.** The deploy's ordering —
build, scan, publish, verify authority, apply, release — is what makes provenance
trustworthy. A rollback reaches into that history; it does not create a new path around it.

**Retention is bounded.** Keeping every tag forever trades one defect for a slow leak. State
the number kept and why.

**Do not roll the frontend and API independently.** They ship together; a rollback that
moves one is how a UI meets an API it was never built against.

## Done when

- A previous deployment is reachable. Whether by retaining tags for a bounded number of
  revisions, pinning by revision rather than tag, or another mechanism, the evidence states
  the choice and what it costs.
- **A rollback is performed against the live product**, and the readback shows the previous
  commit serving on both Cloud Run and Hosting.
- **A roll-forward restores current state**, shown the same way. Leaving production on an
  old version is not a successful test.
- Rolling back to a version whose revision no longer exists at all is still refused, and
  shown refusing. Retention is bounded, so this case is reachable and must fail closed.
- The policy's existing refusals still hold: preflight releases, unpinned rewrites, a pin to
  a newer commit, malformed input. Show them still refusing.
- `0004-E05-T02` is set `done` in the same change, with its live evidence appended. It has
  been waiting on exactly this.


Plus the two live runs. A rollback proven only in tests is the thing this packet exists to
